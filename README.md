# Fitinerary

## Problem Statement

Planning a city trip is not just picking attractions. The hotel changes travel time, transport cost, and what can realistically fit into each day. Fitinerary helps a traveller compare those trade-offs instead of treating hotel choice and itinerary planning as separate decisions.

Current coverage is Tokyo sample data: 12 attractions, estimated travel times/fares, and 3 fictional hotels used for demonstration. It is not live travel, price, or opening-hours data.

## Solution Overview

Fitinerary is a Vue frontend plus a FastAPI backend. The backend validates sample data, solves itinerary and hotel-comparison optimisation problems with OR-Tools CP-SAT, checks every returned plan with an independent validator, and optionally uses an LLM for natural-language interpretation and explanations.

The optimisation engine makes the planning decisions. The LLM interprets natural language and generates explanations from server-computed facts. Validation checks computed results before they are shown.

## Key Features

- Hotel comparison by true cost: rooms, admissions, estimated transport, travel time value, and missed-preference penalty.
- Itinerary optimisation with must-visits, skips, pace, budget, day window, locked activities, unknown-hour controls, and labelled approximate results.
- Replanning that queues edits, requires confirmation before removing a must-visit, and shows an explicit diff.
- Independent feasibility report for opening hours, travel gaps, overlaps, budget, locks, must-visits, and data-quality warnings.
- Proof page generated from repository artifacts, including evaluation, hardening, test summaries, and safety risks.
- Keyboard-accessible controls and equivalent list information for the map itinerary.

Screenshots and demo recording live in `docs/screenshots/` after running `cd frontend && node scripts/take-screenshots.mjs`.

## AI Integration

- Natural-language trip parsing: an LLM can turn user text into an editable draft preference form.
- Natural-language replanning: an LLM can propose operations, but the user must explicitly apply them.
- Explanations: the backend gives the LLM only computed facts; grounding checks reject unsupported numbers/names and fall back to a template.
- Connection: by default the backend calls the model provider directly. If `LLM_BASE_URL` is set it calls that third-party gateway instead, and the cleaned text and computed facts pass through the gateway to the provider (the host is shown in `/health` and on the Proof page; see `docs/PRIVACY.md`).
- Sample mode: without `LLM_API_KEY` and `LLM_MODEL`, Fitinerary still works using forms, optimisation, validation, hotel comparison, replanning, and template explanations.

## External Tools & Datasets

- Backend: Python, FastAPI, Pydantic, OR-Tools CP-SAT, pytest.
- Frontend: Vue 3, Vite, Bootstrap, Leaflet/OpenStreetMap tiles, Vitest, Playwright, Lighthouse.
- Dataset: hand-built Tokyo sample attractions and estimated travel matrix generated by `backend/scripts/build_travel_matrix.py`.
- Hotels are fictional where applicable. Travel times and costs are estimates, not guaranteed live information.

Evaluation methodology is documented in `docs/EVALUATION.md`; generated results are in `docs/eval-results.md` and `docs/eval-results.json`.

## Installation & Setup

Backend:

```bash
cd backend
python -m venv .venv
. .venv/bin/activate
pip install -r requirements-dev.txt
.venv/bin/uvicorn app.main:app --port 8000
```

Frontend:

```bash
cd frontend
npm install
printf 'VITE_API_BASE_URL=http://localhost:8000\n' > .env
npm run dev
```

Verification commands:

```bash
cd backend && .venv/bin/pytest
cd frontend && npm test
cd frontend && npm run e2e
cd backend && python scripts/run_hardening_checks.py
cd backend && python scripts/run_evaluation.py --full
```

Release build:

```bash
cd frontend
VITE_API_BASE_URL=https://your-backend.example npm run build:release
```

Deployment instructions, environment variables, CORS, solver limits, health checks, security headers, live smoke tests, and rollback notes are in `docs/DEPLOY.md`.

## AI Safety & Limitations

Fitinerary is designed to avoid overclaiming:

- Sample data is labelled; Tokyo coverage does not imply real-time accuracy.
- Unknown prices and hours are surfaced instead of silently guessed.
- The LLM cannot set confirmation flags or directly execute replans.
- Prompt-injection tests verify user and place text are treated as data.
- The safety log maps risks to safeguards and tests in `docs/SAFETY_LOG.md`.
- Evidence is generated from files; full backend-suite results are separated from partial runs.

Known limitations: no public holidays, no live transit, no real hotel inventory, no user study, walking-limit preference is documented as unmodelled, and live LLM quality has not been measured unless `docs/llm-live-eval.md` is generated.
