# Local quality upgrade — audit and implementation design

Audit date: 2026-10-18. This is an engineering assessment, not independent testing or a judging result. Historical live prompt-v4 results do not evaluate the new copilot.

The existing architecture already supports strict extraction, verified repair previews, apply-time fingerprint/expected-value checks, dynamic style proposals, an independent schedule validator, a bounded Trade-off Explorer, manual comparison, and a what-if copy/apply workflow. Keep these. The deterministic optimiser remains the only scheduling authority.

The weakest journey is the gap between those controls: on Your Trip a traveller cannot ask why a result occurred or discover the right next control. Omission copy also overstates causality: an optional sight may be excluded by schedule interactions, not solely because its marginal cost exceeds a penalty. Style tags can silently resolve contradictory priorities by tag order. Field verification exists in the dataset but the places API exposes only coarse sample labels.

|---|---|---|---|---|---|
| Contextual copilot | Connect questions to actual plan evidence and existing controls | Classify bounded intent and copy a named place | Rebuild schedule, independent validator, current fingerprint, typed evidence; no model prose or mutations | Medium; one bounded classification, no solver for feasible plan | Misclassification; malicious mock replies, schema failures, stale/invalid plans, UI tests; live suite pending approval |

Data audit: all four city packs remain sample mode. Hotel identities and rates are fictional; travel matrices are straight-line estimates. Existing Singapore field verification is the best demonstration starting point. A source-checked attraction field is not a verified hotel price or route. No real routing provider is connected; credential, licensing, freshness and cost review would precede integration. Do not replace fictional hotel identity with a real property while retaining a fictional rate. No new travel facts are inferred from model output.

Copilot contract: user question → bounded JSON intent (or explicit quick-question operation) → strict schema → allowlisted read operation → server-rebuilt schedule / solver result → independent validator → typed facts, calculations, preferences and uncertainty → deterministic explanation → optional navigation to existing controls. No tools, autonomous loop, hidden prompt disclosure, raw output echo, mutation or confirmation flag is available to the model. Infeasible client results are recomputed; feasible schedules are rebuilt. A fingerprint is a stateless consistency check, not authentication or proof of server ownership. Client preferences remain user-owned in this stateless app.

Scope limits: multi-plan reasoning and scenario simulation use the existing Explorer and What-if controls; the copilot does not accept client-supplied alternatives as facts. Benchmark and participant study distinguish calculated benefit from subjective clarity. Paid live evaluation and genuine participant observations must remain unclaimed until conducted.

Legitimate assertion updates: omission component assertions now require uncertainty rather than an unsupported marginal-cost explanation. The Proof integration assertion derives freshness from the generated code fingerprint instead of assuming the historical gold report matches every future implementation. No test count or threshold is lowered.

The backend historical-report assertion likewise checks the preserved original stamp's format rather than demanding a fresh paid run after every code edit. Python/Node hash equality and frontend stale/current/missing tests still enforce freshness. The adversarial harness distinguishes the existing, labelled exact user-input echo from derived model/plan assertions; it retains the entire API response for inspection.

Apply-path finding: `_optimise_core` returned validator findings, but the repair route previously returned them as a successful replacement even when infeasible. Added an explicit apply-time rejection gate, with separate solver-infeasibility and independent-validator-failure tests and a gate-removal mutation. Conditional valid results remain labelled conditional and are still allowed after confirmation.

Legitimate safety assertion update: `test_an_infeasible_repair_is_never_presented_as_feasible` now requires HTTP 422 and absence of a replacement result/preferences. Its former HTTP 200/infeasible expectation encoded the old replacement behavior; the new assertion enforces the stronger apply-time gate.
